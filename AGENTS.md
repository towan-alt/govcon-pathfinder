# AGENTS.md

## Rules

- Display headings must pair a responsive `text-*` size with an important leading utility (`!leading-[x]`). Responsive `text-*` utilities emit their own line-height inside a media query and silently override a plain `leading-*`, which made large headings render with line-height below font-size and overlap lines.
- All published credibility figures live in `src/lib/brand.ts` (`BRAND`, `STATS`, `FIGURES`) and components must read them from there. Hardcoded numbers in components drift and produce contradictory claims across pages.
- Colors and fonts come only from tokens in `src/index.css` (`--navy`, `--gold`, `--teal`, etc.); never hardcode hsl/hex in components. Hardcoded values drifted from the brand guide across pages.
- Training funnel config (offer list, Square product catalog and static Square link fallbacks, BOOKING_URL/STARTER_KIT_URL/REPLAY_VIDEO_URL, session scheduling, lead/result storage keys) lives in `src/lib/funnel.ts`; pages read from it so the offer stays consistent everywhere.
- Payments run through Payhip: buy buttons link to hosted Payhip checkout URLs in `PAYHIP_PRODUCTS` (`src/lib/funnel.ts`, mirrored in `supabase/functions/_shared/payhip.ts`), `payhip-webhook` records each sale idempotently in `purchases` (keyed on sale_id) and runs fulfillment, and `payhip-lookup` lets confirmation pages verify a buyer's email. The browser must never set its own price, and Square/Stripe are no longer used.
- Evergreen training: registrations and the follow-up queue live in `training_registrations` / `training_messages` (service-role only, accessed through the `training` function); `training-automation` (pg_cron every 5 min, TRAINING_CRON_SECRET bearer) resolves each queued message at send time and skips it when its condition no longer holds. All follow-up copy lives in `supabase/functions/_shared/training-templates.ts`; channels without secrets are marked skipped, never failed.
- Assessment follow-up shares the `training_messages` queue (`sequence` = training|assessment, keyed by `assessment_email`) and the same `training-automation` cron; results, consent log and SMS opt-outs live in `assessment_results`, `consent_log`, `sms_opt_outs` (service-role only, via the `assessment` function). All assessment copy lives in `supabase/functions/_shared/assessment-templates.ts`; one engine avoids duplicate sends.
- NAICS opportunity reports: `naics-report` queries SAM.gov (SAM_GOV_API_KEY) for the last 90 days of open notices and emails them via Resend; each request is logged in `naics_reports` (service-role only), and missing keys mark the row skipped. Signups also land in `naics_subscriptions`; `naics-digest` (pg_cron hourly 13:00-20:00 UTC Mondays, TRAINING_CRON_SECRET bearer, lease lock in `naics_digest_state`, 40 per run) emails the last 7 days of notices once per week per subscriber. Email rendering is shared in `_shared/naics.ts`.
- SEO head tags per route live in `src/components/RouteSeo.tsx` (react-helmet-async); sitewide JSON-LD lives in `index.html`. One map keeps titles/canonicals consistent and private funnel pages noindexed.
- Client portal: `clients` and `client_documents` tables plus the private `client-documents` bucket are service-role only; all client access goes through the token-gated `portal` edge function (portal_token in `clients`), never direct table or storage reads. `square-verify` creates the client row, sends the onboarding email, and handles the 14-day $497-to-VIP credit with single redemption.
- Readiness Review credit offer: `payhip-webhook` queues four `sequence = credit` rows in `training_messages` (keyed by `assessment_email`) on each $497 purchase; `training-automation` skips them once the credit is redeemed, expired or a VIP purchase exists. Copy lives in `supabase/functions/_shared/credit-templates.ts`, so one cron engine handles every follow-up.
- Until a Payhip URL is set, `PayhipCheckoutButton` links to `/contact?interest=<product>` so buy buttons never dead-end.
- SAM.gov filter configuration (`samgov_naics`, `samgov_keyword_groups`, `samgov_keywords`, `samgov_settings` single row id=1, `samgov_ai_profile` single row id=1) is edited only on `/samgov` and is admin-only through RLS `has_role(auth.uid(),'admin')` with roles in `user_roles`; future SAM.gov/AI processing must read these tables, never a second hardcoded copy.
- The SAM.gov API key lives AES-GCM encrypted (SAMGOV_KEY_ENCRYPTION_SECRET) in `samgov_api_credentials` (service-role only); only the admin-checked `samgov-credentials` function touches it and returns last4/status, never the key. Server code reads it via `_shared/samgov-key.ts` `getSamgovApiKey()`, so the secret never reaches the browser.
- SAM.gov retrieval is manual and step-based: `samgov-fetch` (admin-checked) runs start -> naics (one call per active code, paginated with per-run request cap) -> finish so the page shows real progress; it upserts raw notices into `samgov_opportunities` (unique notice_id, full raw_data) and logs each run in `samgov_fetch_runs`. Both tables are admin-read via RLS, written only by service role.
